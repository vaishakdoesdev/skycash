# Sky Cash Scenario Evaluation Service

This document defines the methodology, metric definitions, mathematical formulas, and sign conventions implemented in [`backend/app/engine/scenarios.py`](file:///D:/skycash/backend/app/engine/scenarios.py).

---

## 1. Purpose & Scope

The Scenario Evaluation Service aggregates and contrasts estate-wide placement configurations to provide decision support across four primary scenarios:
1. **Current Placement (Baseline)**: The actual deployment locations of all workloads as recorded in inventory.
2. **Recommended Feasible Placement**: The placement generated by the deterministic decision engine that minimizes cost while strictly satisfying all hard compliance, capacity, and dependency constraints.
3. **Private-DC-First Feasible Scenario**: Retains as many compliant workloads on-premise as usable hardware capacity allows, spilling over to approved Indian clouds only when capacity is exhausted.
4. **Cloud-Prioritized Feasible Scenario**: Migrates all eligible workloads (non-restricted, without strict Karnataka residency mandates) to approved Indian cloud regions.

---

## 2. Metric Definitions & Formulas

### 2.1 Projected Monthly Cost
All costs are calculated on a standardized **monthly billing interval** (720 hours) in **INR**.
- **Private Data Centre**:
  $$\text{Monthly Cost} = \left(\sum \text{allocated\_cores} \times \text{rate}_{\text{cpu}} + \sum \text{allocated\_ram} \times \text{rate}_{\text{ram}} + \sum \text{allocated\_disk} \times \text{rate}_{\text{storage}}\right) \times \left(1 + \frac{\text{PUE}}{100}\right)$$
- **Public Cloud**:
  $$\text{Monthly Cost} = \sum \text{allocated\_cores} \times \text{rate}_{\text{vcpu}} + \sum \text{allocated\_ram} \times \text{rate}_{\text{ram}} + \sum \text{allocated\_disk} \times \text{rate}_{\text{ssd}} + \sum \text{egress\_gib} \times \text{rate}_{\text{egress}}$$

> [!NOTE]
> **Estimate Disclaimer**: Values are labeled as projections based on amortized rates and 720-hour monthly baselines. They are decision-support estimates, not billing invoices.

---

### 2.2 Cost Differences & Sign Convention

$$\text{Absolute Cost Difference} = \text{Scenario Cost} - \text{Baseline Current Cost}$$
$$\text{Percentage Cost Difference} = \frac{\text{Absolute Cost Difference}}{\text{Baseline Current Cost}} \times 100$$

#### Formal Sign Convention:
- **Negative ($< 0$)**: Indicates a **cost reduction / operational savings** compared to baseline.
- **Positive ($> 0$)**: Indicates a **cost increase / premium** compared to baseline (typically incurred to remediate non-compliant legacy placements).
- **Zero ($0.0$)**: Indicates parity with the baseline.

---

### 2.3 On-Premise Resource Utilization & Headroom

To strictly prevent double-counting, each workload assigned to the Private DC is accounted for exactly once per dimension:
- **Compute CPU Cores**:
  $$\text{Allocated} = \sum_{w \in \text{DC Workloads}} w.\text{allocated\_cpu\_cores}$$
  $$\text{Headroom} = \text{usable\_cpu\_cores} - \text{Allocated}$$
  $$\text{Utilization \%} = \frac{\text{Allocated}}{\text{usable\_cpu\_cores}} \times 100$$
- **Memory RAM (GiB)**:
  $$\text{Allocated} = \sum_{w \in \text{DC Workloads}} w.\text{allocated\_ram\_gib}$$
  $$\text{Headroom} = \text{usable\_ram\_gib} - \text{Allocated}$$
- **Persistent Storage (GiB)**:
  $$\text{Allocated} = \sum_{w \in \text{DC Workloads}} w.\text{allocated\_storage\_gib}$$
  $$\text{Headroom} = \text{usable\_storage\_gib} - \text{Allocated}$$

#### Capacity Violation Criteria:
A resource dimension is marked violated if $\text{Allocated} > \text{usable\_capacity}$. The deficit amount is recorded as $\text{Allocated} - \text{usable\_capacity}$.

---

### 2.4 Dependency Group Preservation

Mandatory co-location clusters discovered via union-find connected components must remain unified:
$$\text{Preservation Fraction} = \frac{\text{Preserved Groups}}{\text{Total Mandatory Groups}}$$
- A mandatory group is **preserved** ($= 1$) if and only if all members in the cluster are assigned to the exact same valid placement.
- If any member is split across different locations, the group is broken ($= 0$) and the scenario is marked **infeasible** (`is_feasible = False`).

---

### 2.5 Compliance Violations

Every placement in a scenario is checked against:
1. Cloud administrative approval status.
2. Sovereign and state residency mandates (`KARNATAKA_DC_ONLY`, `INDIA_ONLY`).
3. Data classification ceilings (`RESTRICTED` forbidden in cloud).
4. Required compliance certifications (`RBI_LOCALIZATION`, etc.).

> [!IMPORTANT]
> For any recommendation set accepted for adoption, **compliance violations must be strictly zero** (`compliance_violations_count == 0`). Hard compliance constraints are never relaxed or overridden by cost savings.

---

### 2.6 Feasibility Standard

A scenario is marked **feasible** (`is_feasible = True`) if and only if:
1. `compliance_violations_count == 0`
2. `capacity_violations_count == 0` (no headroom breaches in on-premise DC)
3. `mandatory_dependency_groups_fraction == 1.0` (all mandatory co-location groups preserved)
4. No workloads remain unassigned.

---

### 2.7 Flagging Incomplete Assumptions

If operational telemetry or configuration assumptions are incomplete (e.g. network egress volume not measured), the service flags the affected metric in `unconfirmed_metrics` (e.g. `"Outbound network egress volume was unconfirmed in telemetry and modeled as 0.0 GiB/month"`) instead of fabricating a precise figure.
